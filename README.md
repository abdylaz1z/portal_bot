# Telegram-бот ОшТУ

Асинхронный бот на Python 3.11 с aiogram 3, Playwright и PostgreSQL. Он получает капчу со страницы портала, передаёт её пользователю в Telegram и сохраняет сессионное состояние портала для следующих запросов. SQLite используется только как источник данных при первоначальном переносе.

## Запуск локально

1. Установите Python 3.11, PostgreSQL и зависимости:

   ```bash
   python3.11 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   playwright install --with-deps chromium
   ```

2. Создайте `.env` на основе `.env.example`, укажите `BOT_TOKEN` и задайте `DATABASE_URL` для PostgreSQL.
3. Запустите бота:

   ```bash
   python -m app.main
   ```

## Запуск через Docker Compose

Используйте эту инструкцию для первого запуска в одном экземпляре или для
переноса старой SQLite-базы. При работе на сервере университета следуйте также
разделу «Передача и запуск на сервере университета».

Для PostgreSQL задайте в `.env` пароль для базы. Сгенерируйте URL-безопасный пароль:

```bash
printf '\nPOSTGRES_PASSWORD=%s\n' "$(openssl rand -hex 32)" >> .env
```

Существующий `DATABASE_URL` из `.env` можно оставить: Compose задаёт приложению
адрес PostgreSQL отдельно, а SQLite-файл используется как источник для переноса.

Перед запуском приложения перенесите записи из существующей SQLite-базы в пустую
PostgreSQL-базу. Команда не удаляет и не изменяет SQLite-файл и отказывается
перезаписывать непустые таблицы PostgreSQL. Если SQLite-файл не переносится или
данные уже импортированы в PostgreSQL, этот шаг пропустите:

```bash
docker compose up -d postgres
docker compose run --rm --no-deps oshtu-bot python -m app.migrate_sqlite_to_postgres
docker compose up --build -d oshtu-bot
```

Команда переноса читает SQLite-файл в режиме только для чтения. После проверки
работы PostgreSQL сохраните резервную копию `data/oshtu_bot.db`; не удаляйте её
до проверки перенесённых данных. PostgreSQL хранит данные в именованном томе
`postgres_data`. Логи — в `logs/bot.log` (ротация 10 MB, хранение 7 дней).
Расписание целиком сохраняется в PostgreSQL отдельно для аккаунта и выбранной группы. При нажатии кнопки бот сразу показывает сохранённую копию; обновление с портала выполняется в фоне не чаще раза в неделю. При проверке неизменившееся расписание не перезаписывается, а новая копия сохраняется и отправляется пользователю только при обнаружении изменений. Если портал временно недоступен, последняя сохранённая копия остаётся доступна, в том числе после недели ожидания. После первого успешного получения данные уже доступны без обращения к порталу. Даты в заголовках обновляются при показе кэша.
Преподаватели и успеваемость также сохраняются в PostgreSQL и доступны из последнего успешного кэша при временной недоступности портала.

Запустить проверки кэша расписания можно командой `python -m unittest discover -s tests`.

## Подготовка к масштабированию

Обычный режим использует long polling и должен работать в одном экземпляре. Для
нескольких экземпляров предусмотрен профиль `scalable`: HTTPS webhook через
Caddy, шлюз с маршрутизацией одного Telegram-пользователя к одному worker,
Redis для FSM-состояний и отдельный единственный планировщик. Данные приложения
остаются в PostgreSQL. Redis и шлюз не публикуются напрямую в интернет.

Перед включением webhook обязательно:

1. Создайте DNS-запись `A` для поддомена бота на публичный IP сервера. Откройте
   входящие TCP-порты `80` и `443`. Caddy должен иметь возможность получить и
   продлевать TLS-сертификат. Если университет использует общий reverse proxy,
   согласуйте маршрут до контейнера с администраторами вместо публикации Caddy
   на занятых портах.
2. В `.env` задайте `WEBHOOK_DOMAIN` и `WEBHOOK_PUBLIC_URL` одним и тем же доменом
   (например, `bot.example.org` и `https://bot.example.org`) и замените все
   примеры секретов настоящими значениями.
3. Сгенерируйте отдельный секрет webhook и безопасно внесите его в `.env`:

   ```bash
   printf '\nWEBHOOK_SECRET=%s\n' "$(openssl rand -hex 32)" >> .env
   ```

4. Убедитесь, что старый polling-экземпляр остановлен **на всех серверах**.
   Одновременно polling и webhook для одного токена запускать нельзя. При остановке
   старого экземпляра в этом Compose-проекте:

   ```bash
   docker compose stop oshtu-bot
   ```

5. Запустите шлюз, Redis, единственный планировщик и нужное количество workers:

   ```bash
   docker compose --profile scalable up -d --build \
     --scale bot-worker=3 \
     postgres redis bot-scheduler webhook-gateway caddy bot-worker \
   ```

Проверка состояния и логов:

```bash
docker compose --profile scalable ps
docker compose --profile scalable logs --tail=100 bot-worker bot-scheduler webhook-gateway caddy
```

После запуска проверьте `https://<WEBHOOK_DOMAIN>/healthz`, логи Caddy и worker,
а также `getWebhookInfo` через Telegram Bot API. Убедитесь, что обновления
обрабатываются и бот отвечает в Telegram.

## Передача и запуск на сервере университета

Передайте серверной команде исходный проект и эту инструкцию. Не включайте в
архив или репозиторий `.env`, токен Telegram, `data/oshtu_bot.db`, резервные
копии базы и логи: в базе могут быть действующие сессии портала и Telegram ID.
Секреты передавайте только через согласованный защищённый канал. Шаблон
настроек находится в `.env.example`; сам `.env` уже исключён из Git и Docker
build context.

Попросите администраторов до запуска подтвердить:

- ОС Linux с Docker Engine и Docker Compose v2; доступ к registry для загрузки
  Docker-образов.
- Постоянный серверный адрес и DNS-поддомен бота, например `bot.oshtu.kg`.
- Возможность направить HTTPS-трафик на сервер: TCP 80/443 для Caddy либо
  готовый университетский reverse proxy/TLS ingress.
- Исходящий доступ от контейнеров к Telegram Bot API и `portal.oshtu.kg`.
- Постоянные диски/тома для PostgreSQL, Redis и TLS-сертификатов, резервное
  копирование PostgreSQL и порядок восстановления.
- Какой вариант данных нужен: чистая установка, SQLite-источник или уже
  существующая PostgreSQL-база.

Порядок установки после подготовки DNS и сервера:

1. Загрузите проект на сервер. Создайте рабочий `.env`:

   ```bash
   cp .env.example .env
   chmod 600 .env
   ```

   Внесите токен бота и согласованные настройки. Установите длинный
   URL-безопасный пароль PostgreSQL:

   ```bash
   openssl rand -hex 32
   ```

   Скопируйте полученное значение в `POSTGRES_PASSWORD`. Задайте домен в
   `WEBHOOK_DOMAIN` и `WEBHOOK_PUBLIC_URL`; создайте отдельный случайный
   `WEBHOOK_SECRET`. Не используйте `replace-me` из шаблона.

2. При переносе старой SQLite-базы передайте файл отдельно защищённым способом
   и разместите его как `data/oshtu_bot.db`. Установите права доступа:

   ```bash
   chmod 600 data/oshtu_bot.db
   ```

   После этого создайте PostgreSQL и выполните миграцию **один раз**:

   ```bash
   docker compose up -d postgres
   docker compose run --build --rm --no-deps oshtu-bot \
     python -m app.migrate_sqlite_to_postgres
   ```

   Миграция читает SQLite в режиме только для чтения и откажется писать в
   непустые целевые таблицы. Для чистой установки пропустите её. Для миграции
   существующей PostgreSQL-базы используйте согласованный `pg_dump`/`pg_restore`,
   а не SQLite-мигратор. Сохраните проверенную резервную копию источника до
   завершения приёмки.

3. Остановите polling-экземпляр на старом сервере, чтобы один токен Telegram
   обслуживался только webhook-режимом. Затем запустите масштабируемые сервисы
   командой из раздела «Подготовка к масштабированию».

4. Проверьте здоровье контейнеров, TLS, webhook в Telegram и тестовые сценарии
   `/start`, авторизации, расписания и временной недоступности портала.
   Не удаляйте старый сервер и резервные копии до завершения приёмки.

Контейнеры не публикуют PostgreSQL, Redis или внутренние HTTP-порты worker
напрямую в интернет. Не открывайте эти порты в firewall. Для доступа к БД
администраторам настройте защищённый внутренний канал, а не публичную публикацию
PostgreSQL.

Число workers и их ресурсы должен определить оператор по измерениям. Playwright
запускает Chromium в каждом worker; портал может ограничивать частоту запросов.
Несколько контейнеров сами по себе не гарантируют обслуживание десятков тысяч
одновременных запросов. До объявления такой пропускной способности нужны
нагрузочные испытания на согласованной инфраструктуре и мониторинг задержек,
ошибок Telegram/портала, памяти, CPU, очереди обновлений и подключений к БД.
Суммарный верхний лимит подключений PostgreSQL ориентировочно равен
`количество workers × (DATABASE_POOL_SIZE + DATABASE_MAX_OVERFLOW)` плюс запас
для планировщика и обслуживания. При перезапуске или удалении worker активная
браузерная сессия авторизации с капчей теряется; пользователю нужно будет начать
вход заново.

## Использование

- Кнопки меню — открыть расписание, преподавателей, успеваемость и настройки. В режиме расписания доступны кнопки «Сегодня», «Вчера», «Завтра», «Общая неделя» и отдельный выход обратно в главное меню.
- «🔐 Войти в портал» — начать или повторить авторизацию.
- «❌ Отмена» — отменить ввод логина, пароля или капчи.
- После входа бот предлагает выбрать институт, курс и группу из списков портала; выбор сохраняется в PostgreSQL и применяется к расписанию.
- Семестр в расписании выбирается автоматически по локальной дате ОшТУ: осенний — с сентября по 1 октября, весенний — в остальные даты.
- Команды `/start`, `/login` и `/cancel` также поддерживаются.
- Пароль не сохраняется в базе данных. После получения бот пытается удалить сообщение с паролем; пароль остаётся только на время незавершённого входа в оперативной памяти процесса.
- В PostgreSQL сохраняются cookies, LocalStorage портала и выбранные институт, курс и группа. Ограничьте доступ к базе данных и её резервным копиям.
- В PostgreSQL хранятся последние успешно полученные ответы портала для показа при временном сбое сайта.
- «Настройки / Выход» удаляет локально сохранённую сессию бота.

## Селекторы портала

Для капчи используется `#captchaImage`, как указано в ТЗ. Портал является SPA; его внутреннюю разметку личных страниц нельзя определить по публичной странице входа. Если поля авторизации или элементы расписания, преподавателей и оценок изменятся, переопределите CSS-селекторы через переменные `PORTAL_*_SELECTOR` в `.env`.

Для точного выбора дня укажите `PORTAL_SCHEDULE_DATE_SELECTOR`, а для перехода к следующей неделе — `PORTAL_SCHEDULE_NEXT_SELECTOR`. Без селектора даты бот извлекает отображаемый порталoм список и пытается выделить нужный день по заголовкам.
